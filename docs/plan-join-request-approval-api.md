# Plan: Join Request Approval API

**PRD:** @docs/prd-join-request-approval-api.md
**Дата:** 2026-08-23

## Фазы реализации

### Фаза 1: Список pending-заявок и approve/reject владельцем

**Цель:** Owner может получить список pending-заявок по своим проектам и одобрить/отклонить конкретную заявку; доступ к approve/reject ограничен владельцем проекта.
**Затрагивает:** backend
**Задачи:**

- [x] Реализовать `GET /join-requests/pending` (или аналог) с `verifyToken`: возвращает pending-заявки по проектам, где текущий пользователь — owner, включая данные заявителя
- [x] Реализовать `POST /join-requests/:id/approve` с `verifyToken`: проверяет, что текущий пользователь — owner проекта заявки, иначе 403 без изменения статуса
- [x] В `approve` — атомарно (в транзакции) перевести заявку в статус approved и создать `ProjectMember` с ролью member для заявителя
- [x] Реализовать `POST /join-requests/:id/reject` с `verifyToken`: проверяет owner'а (403 без изменения статуса при отказе), иначе переводит заявку в статус rejected без добавления участника
- [x] Обработать граничные случаи: заявка не найдена, заявка не в статусе pending

**Когда готова:** Тесты подтверждают: owner получает список pending-заявок только по своим проектам; не-owner не может получить список чужого проекта; approve переводит заявку в approved и добавляет участника с ролью member; reject переводит заявку в rejected без добавления участника; approve/reject не-владельцем возвращает ошибку доступа и не меняет статус заявки.

### Фаза 2: Счётчик pending-заявок

**Цель:** Owner может получить количество pending-заявок по своим проектам для отображения счётчика/бейджа.
**Затрагивает:** backend
**Задачи:**

- [x] Реализовать `GET /join-requests/pending/count` (или аналог) с `verifyToken`: возвращает число pending-заявок по всем проектам, где текущий пользователь — owner

**Когда готова:** Тесты подтверждают: owner получает корректное количество pending-заявок по своим проектам; пользователь без своих проектов/заявок получает 0.
