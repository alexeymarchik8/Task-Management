# Plan: User Login API

**PRD:** docs/prd-user-login.md
**Дата:** 2026-08-23

## Фазы реализации

### Фаза 1: Эндпоинт логина с базовой проверкой учётных данных

**Цель:** Минимальный рабочий путь — пользователь может залогиниться с верными email/паролем и получить JWT.
**Затрагивает:** backend
**Задачи:**

- [x] Тест: `POST /auth/login` с верными email/паролем возвращает 200 и JWT-токен, новая запись пользователя в БД не создаётся.
- [x] Тест: JWT в ответе корректно подписан (`JWT_SECRET`) и содержит id пользователя, соответствующего переданному email.
- [x] Создать `authRouter`/роут `POST /auth/login` (`src/auth/login.ts`) по аналогии с `register.ts`: поиск пользователя по email через Prisma, сверка пароля через `bcrypt.compare`, генерация токена через существующий `generateToken`.
- [x] Подключить роут в `src/app.ts` под `/auth`.

**Когда готова:** Тесты фазы проходят; `POST /auth/login` с существующим email и верным паролем возвращает `{ id, email, token }`, запись пользователя в БД не создаётся.

### Фаза 2: Единая ошибка авторизации для невалидных попыток

**Цель:** Логин с несуществующим email или неверным паролем отклоняется с одинаковой ошибкой, не раскрывающей причину.
**Затрагивает:** backend
**Задачи:**

- [x] Тест: логин с несуществующим email возвращает ошибку авторизации (без JWT).
- [x] Тест: логин с существующим email и неверным паролем возвращает ту же ошибку авторизации (без JWT).
- [x] Тест: тексты/структура ответа для обоих случаев идентичны (нельзя различить по ответу, какой из факторов не совпал).
- [x] Реализовать в `login.ts` единую обработку: если пользователь не найден или пароль не совпал — вернуть один и тот же статус/тело ошибки.

**Когда готова:** Оба сценария (несуществующий email, неверный пароль) возвращают одинаковую ошибку авторизации; тесты фазы 1 продолжают проходить.
