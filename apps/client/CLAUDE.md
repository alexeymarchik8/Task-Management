# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

React + TypeScript client, built with Vite. Part of the `task-management` npm-workspaces monorepo (see root `CLAUDE.md`).

## Commands

Run from this directory, or via `npm run <script> --workspace=apps/client` from the repo root:

```bash
npm run dev       # start Vite dev server (http://localhost:5173)
npm run build     # tsc -b type-check, then vite build
npm run preview   # preview the production build
npm test          # vitest run — component/unit tests (jsdom)
```

Linting and formatting are run from the repo root (`npm run lint`, `npm run format`), not from this package — the root ESLint config applies React/React Hooks rules to `apps/client/**/*.{ts,tsx}`.

## Architecture

- Entry point: `src/main.tsx` mounts `src/App.tsx` into `index.html`. `App.tsx` only wraps `router/AppRouter` in `auth/AuthContext`'s `AuthProvider` — no routes or page markup live here.
- **Folder structure**:
  - `src/pages/<PageName>/` — one folder per page: `index.tsx` (the page component), `<PageName>.module.scss`, `<PageName>.test.tsx`, and page-only subcomponents under `components/` (e.g. `pages/Register/components/RegisterHeader.tsx`). A `config.ts` and/or `utils/` subfolder is added only when a page actually needs one.
  - `src/components/<ComponentName>/` — same shape as pages (`index.tsx` + `.module.scss` + `.test.tsx`). Subcomponents used only by one component are nested under that component's own `components/` folder rather than living as siblings (e.g. `components/RegistrationForm/components/{EmailField,PasswordField,FormAlert,SubmitButton}/index.tsx`).
  - `src/router/` — `routes.ts` exports two flat `{ path, element }[]` arrays: `protectedRoutes` (pages that need auth + the sidebar) and `publicRoutes` (`/register`, `/login`). `AppRouter.tsx` renders `BrowserRouter`/`Routes`: the `/` → `/dashboard` redirect, `protectedRoutes` nested under a pathless `<Route element={<AppLayout />}>` (so their `path` stays absolute, e.g. `/dashboard`, while `AppLayout` provides the auth guard + sidebar), and `publicRoutes` rendered directly.
  - `src/assets/` — static assets (images, icons, fonts); currently empty (`.gitkeep`).
  - `src/auth/`, `src/api/`, `src/store/`, `src/test/` — unchanged, see below.
- **Routing**: `react-router-dom` (`BrowserRouter`), routes declared in `src/router/routes.ts` (`protectedRoutes`: `/dashboard/:projectId`; `publicRoutes`: `/register`, `/login`) and rendered by `src/router/AppRouter.tsx` (see folder structure above for the protected/public split).
- **State management**: Redux Toolkit. `src/store/authSlice.ts` holds the authenticated `AuthUser` (`id`, `email`) and a `login` reducer that persists the JWT and user to `localStorage` (`token`, `user` keys); `src/store/themeSlice.ts` holds the current `Theme` (`'light' | 'dark'`), initialized from `localStorage` (`theme` key) falling back to `window.matchMedia('(prefers-color-scheme: dark)')`, with a `toggleTheme` reducer that flips it and persists the new value; `src/store/store.ts` exports `createAppStore()` combining both. `src/auth/AuthContext.tsx` wraps this in an `AuthProvider` (creates one store instance per mount via `Provider` from `react-redux`, reading `localStorage` at creation time) and a `useAuth()` hook (`useSelector`/`useDispatch`) — the public API (`AuthProvider`, `useAuth`) is unchanged from the previous Context-based implementation, so callers don't need to know Redux is used underneath. `src/theme/useTheme.ts` is the equivalent read/write hook for the theme slice; it also applies the current theme as `data-theme` on `document.documentElement` via a `useEffect` (see below) — `App.tsx` calls it once unconditionally (in an `AppContent` component nested inside `AuthProvider`, since the hook needs the Redux `Provider` above it) so the attribute is set on every route, including the public `/login`/`/register` pages, even though the toggle button itself only appears once authenticated.
- **API layer**: `src/api/authApi.ts` — thin `fetch` wrapper (`registerUser`, `loginUser`) against the server at `http://localhost:3000`; throws `ApiError` (with `status`/`message`) on non-2xx responses. `src/api/tasksApi.ts` (`listTasks` — takes an optional `TaskFilters` object (`status`/`priority`/`assigneeId`/`search`) appended as query params via `URLSearchParams`, omitted entirely when empty —, `createTask`, `updateTask`, `deleteTask`), `src/api/projectsApi.ts` (`listProjects`, `createProject`, `listMembers`, `updateProject`, `deleteProject`, `leaveProject`, `removeMember`), `src/api/joinRequestsApi.ts` (`joinProject`, `listMyJoinRequests`, `listPendingJoinRequests`, `countPendingJoinRequests`, `approveJoinRequest`, `rejectJoinRequest`, `deleteJoinRequest`), and `src/api/analyticsApi.ts` (`getAnalyticsSummary`) all follow the same pattern, reading the JWT from `localStorage.getItem('token')` and sending `Authorization: Bearer <token>` on every call; all re-export `ApiError` from `authApi.ts` so callers only need one import.
- **Layout & Sidebar**: `src/components/AppLayout/index.tsx` is the element for every `protectedRoutes` entry — it redirects to `/login` if `useAuth().isAuthenticated` is false, otherwise renders `<Outlet />` (the matched page) next to `src/components/Sidebar/index.tsx` (positioned after the content, so it sits on the right). `Sidebar` itself also renders nothing when unauthenticated (defense in depth), and otherwise fetches `listProjects()` on mount and holds the list in local state. It renders, top to bottom: a top bar with `components/ThemeToggle` (button toggling `useTheme()`'s theme, sun/moon icon, right-aligned), `components/ProjectSearch` (controlled input, filters the in-memory project list by name — no server-side search), `components/ProjectList` (each project links to `/dashboard/:projectId`), `components/CreateProjectForm` (calls `createProject`, appends the result to Sidebar's project list on success — no refetch), `components/JoinByCodeForm` (calls `joinProject`, shows either the server's error message — e.g. "Вы уже в проекте" — or a "Заявка отправлена" confirmation), `components/MyJoinRequests` (lists the current user's own join requests with status; a rejected one can be hidden via `deleteJoinRequest`), `components/PendingRequests` (owner view — badge with the pending count for the user's projects, Approve/Reject per request), `components/People` (reads `projectId` via `useParams()` off the currently matched route; empty/inactive when no project is open, otherwise lists that project's members via `listMembers`), `components/InfoButton` (button — `aria-expanded` reflects the open/closed panel state — + panel showing the open project's name, code, and the current user's role, derived from the members list), and `components/ProjectSettings` (another disclosure button + panel, for the open project only): the project's owner sees a rename form (label "Новое название проекта" — deliberately not just "Название проекта", which is `CreateProjectForm`'s own field label and would otherwise collide under Playwright's substring `getByLabel` in e2e) calling `updateProject`, the other members (fetched via its own `listMembers` call, only while open and only for the owner) each with a "Удалить" button, and a "Удалить проект" button; a non-owner instead sees only a "Выйти из проекта" button. All three destructive actions (`deleteProject`, `removeMember`, `leaveProject`) go through the shared `src/components/ConfirmDialog/index.tsx` (message + confirm/cancel buttons) before calling the API. `Sidebar` wires `ProjectSettings`'s callbacks: `onRenamed` patches the project into its own `projects` list (so `ProjectList`/`InfoButton` reflect the new name immediately), `onLeftOrDeleted` drops the project from that list and `useNavigate()`s to `/homepage` (since the dashboard the user was just looking at no longer exists for them), and `onMembersChanged` bumps the same `membersRefreshKey` used after approving a join request, so `People` refetches too.
- **Registration**: `src/components/RegistrationForm/index.tsx` composes `src/components/RegistrationForm/components/{EmailField,PasswordField,FormAlert,SubmitButton}/index.tsx` (loading/disabled state, `role="alert"` error message) and is used by `src/pages/Register/index.tsx` (composing `src/pages/Register/components/RegisterHeader.tsx`), which redirects an already-authenticated user to `/homepage`, redirects to `/homepage` after a successful registration, and links to `/login`.
- **Login**: `src/components/LoginForm/index.tsx` (email/password fields, loading/disabled state, single generic `role="alert"` error that does not reveal whether the email or password was wrong) is used by `src/pages/Login/index.tsx`, which redirects an already-authenticated user to `/homepage`, redirects to `/homepage` after a successful login, and links to `/register`.
- **Dashboard** (project kanban board): `src/pages/Dashboard/index.tsx` reads `projectId` from the route (`useParams`), redirects to `/login` if not authenticated, fetches `listTasks(projectId)` and `listMembers(projectId)` (from `api/projectsApi.ts`) on mount, and renders `src/components/KanbanBoard/index.tsx` (passed both `tasks` and `members`) plus a "+ Новая задача" button that opens `src/components/TaskForm/index.tsx` in create mode. `KanbanBoard` groups the given `tasks` into 5 fixed columns from `src/components/KanbanBoard/config.ts` (`COLUMNS`: Backlog/To Do/In Progress/In Review/Done, matching the server's `TaskStatus` enum) via `src/components/KanbanBoard/components/Column/index.tsx` (forwards `members` through), each rendering `src/components/KanbanBoard/components/TaskCard/index.tsx` (title, description, priority badge, due date, assignee email resolved from `members` by `task.assigneeId` — or "Не назначен" — a status `<select>` that moves the card between columns, an "Изменить" button that opens `TaskForm` pre-filled for that task, and a delete button). `KanbanBoard` also wraps everything in `@dnd-kit/core`'s `DndContext` (a `PointerSensor` with an 8px `activationConstraint`, so plain clicks on the card's inner controls aren't hijacked as drag gestures) so a card can be dragged onto another column — `Column` is a droppable area (`useDroppable({ id: column.status })`, highighted via a `.over` class while a card hovers over it) and `TaskCard` exposes a small "⠿" drag handle button (`useDraggable({ id: task.id })`; only the handle gets `{...attributes} {...listeners}`, not the whole card, so the status `<select>`/delete/edit buttons stay independently clickable) — dropping calls the same `onStatusChange(taskId, status)` prop as the `<select>` fallback, via the pure/unit-tested `src/components/KanbanBoard/dragEnd.ts#handleDragEnd(event, onStatusChange)`. `TaskForm` is a single component used for both create and edit (`task` prop present or not) — it fetches the project's own `listMembers(projectId)` on mount to populate an "Исполнитель" `<select>` (empty option = unassigned) — and on submit calls `createTask`/`updateTask` from `api/tasksApi.ts` (including `assigneeId`) and reports the resulting `Task` back to `Dashboard` via `onSuccess`; `Dashboard` owns the `tasks` array in local state and reconciles it after every create/update/delete (`handleFormSuccess`/`handleStatusChange`/`handleDelete`) rather than refetching the whole list. Above the board, `src/components/TaskFilterBar/index.tsx` (search input + status/priority/assignee `<select>`s, aria-labels "Поиск задач"/"Фильтр по статусу"/"Фильтр по приоритету"/"Фильтр по исполнителю" — deliberately not exact substrings of TaskForm's/TaskCard's own field labels, which matters for Playwright's default substring `getByLabel` matching in e2e) renders the current `TaskFiltersState` (`{ status, priority, assigneeId, search }`, all empty-string when unset) and reports changes via `onChange`; `Dashboard` keeps this state in the URL query string itself (`useSearchParams`, not local `useState`) so a filtered view is a shareable/reload-safe link, and refetches `listTasks(projectId, filters)` whenever any filter value changes.
- **Home page (analytics)**: `src/pages/Home/index.tsx` — self-contained auth-redirect (`useAuth()` + `Navigate to="/login"`), fetches `getAnalyticsSummary()` on mount, renders total tasks / per-status breakdown / % done cards plus a per-project list with a mini breakdown for each; clicking a project navigates to `/dashboard/:projectId` (`useNavigate`); renders an empty state when the user has no projects/tasks.
- **Styling**: SCSS Modules (`*.module.scss`, co-located with their component) plus a global `src/index.scss`; see [Frontend conventions](#frontend-conventions). Colors/radii/shadows/etc. are CSS custom properties on `:root` — `:root[data-theme='dark']` redefines the same tokens for dark mode (also sets `color-scheme: dark` so native controls like `<input type="date">` and scrollbars follow), toggled by `src/theme/useTheme.ts` (see State management above); component stylesheets should keep using the `var(--color-*)` tokens rather than hardcoding colors so they pick up both themes automatically.
- **Testing**: Vitest + `@testing-library/react` (jsdom environment, config in `vitest.config.ts`, setup in `src/test/setup.ts` — which also polyfills `window.matchMedia` since jsdom doesn't implement it, needed because `themeSlice`'s initial state reads it; coverage via `@vitest/coverage-v8`, run with `npx vitest run --coverage`); test files live alongside source as `*.test.ts(x)`.
- `tsconfig.json` / `tsconfig.tsbuildinfo` drive TypeScript project-reference builds used by `tsc -b`.

## Frontend conventions

- **State management**: use Redux Toolkit (`@reduxjs/toolkit` + `react-redux`) for shared/global application state (e.g. auth, cross-page data). Organize as feature slices (`createSlice`) under a `src/store/` (or per-feature `slice.ts`) structure, with a single `configureStore` root store. Local/UI-only state that doesn't need to be shared still belongs in component state (`useState`/`useReducer`).
- **Component/page decomposition**: every page (`src/pages/`) and component (`src/components/`) is a folder named after it, containing `index.tsx`, a co-located `*.module.scss`, a `*.test.tsx`, and (only when actually needed) a `config.ts` and/or `utils/` subfolder. Avoid large files mixing many JSX elements/responsibilities — split into small, focused pieces composed together. A subcomponent used by only one parent is nested under that parent's own `components/` folder, not placed as a sibling.
- **Routing**: add a new page by adding an `{ path, element }` entry to `src/router/routes.ts` — do not add routes directly in `App.tsx`.
- **Styling**: use a CSS preprocessor (Sass/SCSS) for stylesheets — `.scss` files, one per component (co-located next to the component, e.g. `ComponentName/ComponentName.module.scss`), using SCSS features (nesting, variables, mixins) instead of plain CSS.
